CPU와 RAM 사이 거리 -> 물리적으로 거리가 좀 있음. 일직선으로 보자면 Core <-> Registers <-> L1 Dcache <-> L2 cache <-> DDR2 RAM
GPU와 RAM 사이 거리 -> 더 멂. 일직선으로 보자면 FP <-> Registers <-> L1 cache <-> L2 cache <->GDDR4 RAM
GPU 같은 경우엔, 연산을 맡길 때, 단순 연산보단, 이미지 텍스처 파일을 넘긴다던가 큰 연산에 대한 정보를 넘기는 경우가 많음.
그래서, GDDR4 RAM(공간이 많은 곳)에 옮기고 왓다갔다함.
rootsignature에서 서명할때 중요한건, registers에서 어떻게 활용할건지 선언해줘야함. (registers는 GDDR4 RAM에 비해 상당히 중요하고 작은 공간이므로)

constant buffer view (cbv) -> b 레지스터
shader resource buffer (srv) -> t 레지스터
unordered accessed view (uav) -> u 레지스터

[중간의 큰 단위에 넣어 줄 수 잇는 세가지] 
root constant -> [SetComputeRoot32BitConstant]
root descriptor(포인터마냥 다른 resource를 가리키는 View의 개념) -> [SetGraphicsRootConstantBufferView]
descriptor table -> SetComputeRootDescriptorTable

왜 굳이 descriptor table로 한번 더 타고 가서 만드는지 ?
-> root table은 무한정으로 늘릴 수 있는 것이 아닌, 정해진 최대 제한 용량이 있기 때문.
-> 직접 binding하는 인자들을 무한정 늘려버리면 성능에도 좋지 않음. 고로 descriptor table로 가져와서 성능 향상.

root table 최대 가능 용량 -> DWORD 64개 가능 [DWORD(4bytes) * 64 = 256bytes]

constant buffer 사용법
1) Buffer에 데이터 세팅
2) Buffer의 주소를 register에 전송
-> constant buffer 만으로 여러개의 삼각형을 그리려고 하는 경우, 삼각형의 개수만큼 buffer를 만듬
-> 비효율적인데 ?

constant buffer 규칙
1. 256byte의 배수로 만들어야함 (0, 256, 512, 768 ....)

2. vertex buffer와 다르게 constant buffer에서 map 후 unmap을 바로 사용하지 않는 이유
-> 이 데이터를 계속 사용하여 데이터를 프레임마다 복사할 것이라서

3. mappedbuffer에 어떤 데이터를 집어 넣은 상태에서 GPU가 그 데이터를 읽는 상태에서 우리가 또 그 상태를
건들이게 되면 안됨. GPU가 데이터를 읽어들일때는 건들이면 안됨.
