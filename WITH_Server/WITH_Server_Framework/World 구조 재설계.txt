# World 구조 재설계

0. 재설계 목적
    - 기존 World 구조의 핵심인 WorldService, WorldLeapManager, WorldScheduler의 디커플링
    - World lifecycle state machine, Presence lifecycle state machine, 
      completion / close / destroy 등 운영 정책 요구의 안정적 수용


1. 새 구조의 계층과 책임

    1. Definition/Policy 계층
        - WorldDef를 읽는 순수 정책 계층
        - "어떤 월드가 어떻게 운영되어야 하는가"만 정의


    2. Instance / Runtime 계층
        - 실제 시뮬레이션 컨테이너인 WorldInstance + WorldRuntime
        - 기존 World의 역할을 흡수하되, 정책적 판단은 제외


    3. Lifecycle 관리 계층
        - WorldManager
            - World lifecycle state machine
            - presence lifecycle
            - empty destroy delay
            - completion close
            - fallback close

        - 기존 WorldService의 기능을 확장하여 재구성


    4. Admission 계층
        - WorldAdmissionService
        - 입장 가능 여부와 reservation 판단
            - stage
            - join policy
            - max player count
            - reentry
            - closing / destroy pending 상태
            - in-flight transfer overflow


    5. Transfer 계층
        - WorldTransferService
        - durable transaction 기반 월드 이동 처리
            - WorldTransferRequest
            - WorldTransferTxn (TransferStage)


    6. Scheduling 계층
        - WorldScheduler
        - world stage와 lifecycle command flush를 인지하는 lifecycle-aware scheduler


2. 새 구조의 설계 원칙과 보장 사항

    1. 식별 체계 분리
        - WorldDefId : 월드 정의 ID
        - WorldId : 실제 생성된 런타임 world instance 핸들
        - instanceKey : 같은 WorldDefId 아래 여러 논리 인스턴스를 구분하는 resolve key


    2. lifecycle state machine
        - 새 구조는 World lifecycle, Presence lifecycle, Transfer lifecycle을 
          별도 상태 모델로 표현하여, 월드가 현재 어떤 운영 상태에 있는지를
          코드 레벨에서 명확히 추적 가능하게 하는 것을 목표로 한다.


    3. Transfer의 request / txn 분리
        - Transfer의 입력과 처리 상태를 분리함으로써 처리 도중 상태를
          durable하게 보존하고 이를 운영 중 참고 자료로써 활용한다.


3. 핵심 개념 및 규칙

    1. resolve 입력 규칙
        - explicitTargetId가 있으면 그 WorldId를 우선 사용
            - 이 경우 targetWorldDefId, instanceKey는 무시

        - explicitTargetId가 없으면 targetWorldDefId + instanceKey로 resolve
            - 이 경우 WorldManager::ResolveOrCreate(defId, instanceKey)를 사용


    2. instanceKey 기본 규칙

        1. 공통 규칙
            - instanceKey는 월드 정의 내부의 논리 인스턴스 식별값
            - 같은 의미의 월드는 항상 같은 key를 써야 함
            - 임의 난수 key의 사용을 제한할 것


        2. instanceKey == 0 규칙
            - 0은 singleton/default instance key
            - Persistent 월드에서는 기본적으로 0만 사용
            - Instanced, SessionScoped에서는 0사용 금지


    3. InstanceType 별 resolve 규칙

        1. Persistent
            - instanceKey는 항상 0으로 정규화
            - 같은 WorldDefId에 대해 런타임 인스턴스는 하나만 존재


	    2. Instanced
            - 호출자가 준 instanceKey를 그대로 사용
            - instanceKey != 0
            - 같은 (WorldDefId , instanceKey) 면 같은 월드 재사용


	    3. SessionScoped
            - 세션/매치 단위 key 사용
            - instanceKey != 0
            - 세션 종료 후 lifecycle에 따라 파괴


    4. resolve 실패 규칙

        1. 실패 조건
            - 아래의 조건에서는 ResolveOrCreate가 실패해야 함
                - worldDefId == None
                - WorldDef 조회 실패
                - IntanceType에 따른 instanceKey 정규화 규칙 위반
                - CreationPolicy == PreCreated 인데 기존 월드 없음
                - Registry 생성 실패


        2. 실패 처리
            - 1차 구현에서는 WorldId::Invalid()를 반환하고 내부 로그 추가
            - 추후 ResolveResult와 같은 관리 체계 추가


    5. Transfer 실패 복구 정책

        1. 기본 원칙
            - Transfer는 완전한 원자적 transaction이 아니라,
              단계별 side effect를 남기며 진행되는 durable transaction으로 본다.
            - 따라서 실패 복구는 "전체를 원상복구"하는 방식이 아니라,
              현재 stage까지 반영된 side effect를 기준으로
              취소(cancel) 또는 보상(compensation)하는 방식으로 설계한다.
            - FailTxn은 즉시 Failed로 끝내지 않고,
              stage별 cleanup 정책을 먼저 수행한 뒤 terminal 상태로 전이한다.
            - timeout은 일반 실패와 구분되는 별도 failure reason으로 관리한다.


        2. side effect 발생 시점
            - Requested
                - request만 생성된 상태
                - 아직 side effect 없음

            - SourceValidated
                - source world / source membership 검증만 끝난 상태
                - 아직 side effect 없음

            - TargetResolved
                - target world는 확정되었고
                  presence는 TransferPending 상태로 진입했을 수 있음
                - reservation은 아직 없음

            - AdmissionReserved
                - target admission reservation이 발급되었고
                  reservedSlots가 점유됨

            - TransferContextBuilt
                - source world 기준으로 target import / source release에 사용할
                  transfer context가 확보된 상태
                - transfer context의 내부 payload 구조는 runtime 구현에 종속되며,
                  transfer 계층은 이를 opaque한 이동 컨텍스트로 취급
                - 1차 구현에서는 context는 메모리상의 임시 데이터로 간주

            - TargetImported
                - target import / spawn이 반영되었을 수 있음
                - reservation은 consumed 되었을 수 있음
                - target activePlayers 증가,
                  presence ImportedToTarget 전이가 일부 또는 전체 반영되었을 수 있음

            - SourceReleased
                - source release / despawn이 반영되었고
                  presence CompleteTransfer까지 끝났을 수 있음


        3. stage별 실패 복구 규칙

            1. Requested / SourceValidated 실패
                - reservation cleanup 없음
                - source / target occupancy rollback 없음
                - presence가 TransferPending으로 들어간 흔적이 있으면
                  FailTransfer로 정리
                - txn은 Failed로 종료

            2. TargetResolved 실패
                - reservation cleanup 없음
                - presence TransferPending 정리 필요
                - source / target occupancy rollback 없음
                - txn은 Failed로 종료

            3. AdmissionReserved 실패
                - reservation이 active 상태이면 CancelReservation 수행
                - presence TransferPending 정리
                - source / target activePlayers 변경은 없음
                - txn은 Failed로 종료

            4. TrnasferContextBuilt 실패
                - reservation이 active 상태이면 CancelReservation 수행
                - presence TransferPending 정리
                - transfer context 임시 데이터는 폐기
                - source / target activePlayers 변경은 없음
                - txn은 Failed로 종료

            5. TargetImported 실패
                - reservation이 아직 active면 CancelReservation 수행
                - reservation이 이미 consumed 된 경우에는
                  reservation 복구 대신 target side compensation을 수행
                - target activePlayers 증가가 반영되었으면 해당 수만큼 감산
                - presence ImportedToTarget / TransferPending 흔적 정리 필요
                - 이 구간부터는 rollbackRequired = true 로 표시 가능
                - txn은 Failed로 종료

            6. SourceReleaseFailed
                - 가장 위험한 실패 구간으로 간주
                - target import는 이미 반영되었을 수 있으나
                  source release / presence complete가 불완전할 수 있음
                - 1차 구현에서는 자동 source 복구를 시도하지 않는다
                - rollbackRequired = true 로 표시하고
                  운영 개입 또는 후속 정리 대상으로 남긴다
                - txn은 Failed로 종료


        4. timeout 정책
            - 각 txn은 deadlineSec을 가진다
            - nowSec >= deadlineSec 이면 timeout으로 간주한다
            - timeout은 별도 failure reason(TimedOut)으로 기록한다
            - timeout 시 cleanup은 해당 시점의 stage에 맞는 복구 규칙을 따른다
            - 1차 구현에서는 timeout 후 자동 retry를 수행하지 않는다
            - retryCount는 운영 참고용 기록값으로만 유지한다


        5. fallback 정책
            - fallback은 allowFallback == true 인 요청에 대해서만 허용한다
            - fallback은 초기 단계 실패에만 허용한다

            1. fallback 허용 구간
                - TargetResolveFailed
                - AdmissionRejected
                - TimedOut 이면서 stage <= AdmissionReserved 인 경우

            2. fallback 금지 구간
                - TransferContextBuilt 이후 실패
                - TargetImported 실패
                - SourceReleaseFailed

            3. fallback target 규칙
                - 우선순위 1 : target WorldDef 또는 link rule에 명시된 fallbackWorldDefId
                - 우선순위 2 : 시스템 기본 fallback world
                - fallback은 새로운 request를 만들어 재시도하는 것이 아니라,
                  기존 txn의 실패 cleanup이 끝난 뒤 별도 정책으로 재진입시킨다


        6. rollbackRequired의 의미
            - rollbackRequired == false
                - 일반 cleanup만으로 상태 정리가 가능한 실패
            - rollbackRequired == true
                - target import 또는 source release 이후의 실패처럼
                  자동 정리가 불완전할 수 있는 실패
                - 운영 개입 또는 별도 recovery pass의 대상


        7. 구현상 제약 및 1차 범위
            - 1차 구현에서는 retry 자동 재시도는 도입하지 않는다
            - 1차 구현에서는 fallback도 초기 단계에서만 허용한다
            - 1차 구현에서는 SourceReleaseFailed를 완전 자동 복구하지 않는다
            - snapshot / import / release가 아직 mock 수준인 부분은
              현재 side effect 모델에 맞춰 최소 cleanup만 수행한다

        - 미완료
            - 새 구조의 핵심 골격은 이미 생겼고,
              일부 정책(timeout / cleanup / fallback / reentry)도 반영되었음
            - 그러나 실제 운영 경로 전환 단계는 아직 아님
            - 특히 실제 import-release runtime 경로와 scheduler가 아직 덜 닫힘
            - WorldLeapManager / WorldService 계열 legacy 경로는 아직 참조 기준점으로 남아 있음

        - 남은 작업
            - legacy 호출 경로 차단
            - 새 admission / transfer / presence 흐름을 기본 경로로 연결
            - mock transfer를 실제 world runtime import / release 경로로 치환
            - 운영 중 장애 복구 / fallback / close / destroy 정책 실장
            - 테스트와 migration 검증 완료
