# World 구조 재설계

0. 재설계 목적
    - 기존 World 구조의 핵심인 WorldService, WorldLeapManager, WorldScheduler의 디커플링
    - World lifecycle state machine, Presence lifecycle state machine, 
      completion / close / destroy 등 운영 정책 요구의 안정적 수용


1. 새 구조의 계층과 책임

    1. Definition/Policy 계층
        - WorldDef를 읽는 순수 정책 계층
        - "어떤 월드가 어떻게 운영되어야 하는가"만 정의


    2. Instance / Runtime 계층
        - 실제 시뮬레이션 컨테이너인 WorldInstance + WorldRuntime
        - 기존 World의 역할을 흡수하되, 정책적 판단은 제외


    3. Lifecycle 관리 계층
        - WorldManager
            - World lifecycle state machine
            - presence lifecycle
            - empty destroy delay
            - completion close
            - fallback close

        - 기존 WorldService의 기능을 확장하여 재구성


    4. Admission 계층
        - WorldAdmissionService
        - 입장 가능 여부와 reservation 판단
            - stage
            - join policy
            - max player count
            - reentry
            - closing / destroy pending 상태
            - in-flight transfer overflow


    5. Transfer 계층
        - WorldTransferService
        - durable transaction 기반 월드 이동 처리
            - WorldTransferRequest
            - WorldTransferTxn (TransferStage)


    6. Scheduling 계층
        - WorldScheduler
        - world stage와 lifecycle command flush를 인지하는 lifecycle-aware scheduler


2. 새 구조의 설계 원칙과 보장 사항

    1. 식별 체계 분리
        - WorldDefId : 월드 정의 ID
        - WorldId : 실제 생성된 런타임 world instance 핸들
        - instanceKey : 같은 WorldDefId 아래 여러 논리 인스턴스를 구분하는 resolve key


    2. lifecycle state machine
        - 새 구조는 World lifecycle, Presence lifecycle, Transfer lifecycle을 
          별도 상태 모델로 표현하여, 월드가 현재 어떤 운영 상태에 있는지를
          코드 레벨에서 명확히 추적 가능하게 하는 것을 목표로 한다.


    3. Transfer의 request / txn 분리
        - Transfer의 입력과 처리 상태를 분리함으로써 처리 도중 상태를
          durable하게 보존하고 이를 운영 중 참고 자료로써 활용한다.


3. 핵심 개념 및 규칙

    1. resolve 입력 규칙
        - explicitTargetId가 있으면 그 WorldId를 우선 사용
            - 이 경우 targetWorldDefId, instanceKey는 무시

        - explicitTargetId가 없으면 targetWorldDefId + instanceKey로 resolve
            - 이 경우 WorldManager::ResolveOrCreate(defId, instanceKey)를 사용


    2. instanceKey 기본 규칙

        1. 공통 규칙
            - instanceKey는 월드 정의 내부의 논리 인스턴스 식별값
            - 같은 의미의 월드는 항상 같은 key를 써야 함
            - 임의 난수 key의 사용을 제한할 것


        2. instanceKey == 0 규칙
            - 0은 singleton/default instance key
            - Persistent 월드에서는 기본적으로 0만 사용
            - Instanced, SessionScoped에서는 0사용 금지


    3. InstanceType 별 resolve 규칙

        1. Persistent
            - instanceKey는 항상 0으로 정규화
            - 같은 WorldDefId에 대해 런타임 인스턴스는 하나만 존재


	    2. Instanced
            - 호출자가 준 instanceKey를 그대로 사용
            - instanceKey != 0
            - 같은 (WorldDefId , instanceKey) 면 같은 월드 재사용


	    3. SessionScoped
            - 세션/매치 단위 key 사용
            - instanceKey != 0
            - 세션 종료 후 lifecycle에 따라 파괴


    4. resolve 실패 규칙

        1. 실패 조건
            - 아래의 조건에서는 ResolveOrCreate가 실패해야 함
                - worldDefId == None
                - WorldDef 조회 실패
                - IntanceType에 따른 instanceKey 정규화 규칙 위반
                - CreationPolicy == PreCreated 인데 기존 월드 없음
                - Registry 생성 실패


        2. 실패 처리
            - 1차 구현에서는 WorldId::Invalid()를 반환하고 내부 로그 추가
            - 추후 ResolveResult와 같은 관리 체계 추가


4. 마일스톤 및 진행상황

    1. 상태 모델 및 관리 골격 정리
    목표
        - lifecycle enum, world record, transfer txn, manager 인터페이스 안정화
        - id 체계 고정
        - resolve / admission / transfer / presence가 공유하는 상태 모델 정리

    진행 상황
        - 완료
            - WorldStage / PresenceStage / TransferStage / AdmissionDecision /
              TransferFailureReason 등 핵심 enum 정의 완료
            - AdmissionRequest / AdmissionReservation / AdmissionResult 정의 완료
            - WorldTransferRequest / WorldTransferTxn 정의 완료
            - PresenceRecord 정의 완료

        - 현재 수준
            - 상태 모델의 큰 축은 고정 가능한 수준까지 올라왔음
            - 새 구조의 최소 운영 골격을 설명할 수 있는 데이터 모델이 확보됨

        - 남은 작업
            - 세부 naming 정리
            - validation / result type의 표준화
            - rollback, fault handling, timeout 정책을 상태 모델에 더 엄격히 반영


    2. WorldManager 최소 구현
    목표
        - World resolve / create 흐름을 WorldManager로 이동
        - 기존 WorldService 의존 제거
        - WorldDefId + instanceKey 기반 resolve 규칙을 코드에 반영

    진행 상황
        - 부분 완료
            - WorldRegistry 연동 완료
            - ResolveOrCreate / RegisterPreCreatedWorld 구현 완료
            - resolve index와 world record 등록 경로 구현 완료
            - def 기반 record 초기화(FillRecordFromDef) 구현 완료
            - reservedSlots / inFlightTransfersIn / inFlightTransfersOut accounting 구현 완료
            - closeRequested 마킹 구현 완료

        - 현재 수준
            - 월드 resolve / 생성 / record 등록 / 운영 카운터 관리의 최소 경로는 동작함
            - Persistent / Instanced / SessionScoped resolve 규칙은 WorldResolveRules를 통해
              검증 및 정규화되는 방향으로 연결됨

        - 미구현 / 보강 필요
            - FlushLifecycle 미구현
            - CollectDestroyable 미구현
            - 실제 stage progression(Allocated -> Bootstrapping -> Running -> Closing ...)
              관리 로직 미구현
            - empty destroy delay / completion close / fallback close 정책 미구현


    3. Admission / Transfer 분리 구현
    목표
        - WorldAdmissionService 도입
        - WorldTransferService 도입
        - 기존 WorldLeapManager 의존 제거
        - request / txn / reservation을 분리한 durable flow 확보

    진행 상황
        - 부분 완료
            - WorldAdmissionService 구현 완료
                - stage / closing / join policy / capacity / reentry /
                  in-flight transfer overflow 기반 판단 구현
                - reservation 발급 / consume / cancel / expire 구현

            - WorldTransferService 구현 완료
                - request enqueue
                - txn 저장 및 Tick 기반 progression
                - SourceValidated -> TargetResolved -> AdmissionReserved ->
                  SnapshotBuilt -> TargetImported -> SourceReleased -> Completed
                  단계 전이 구현
                - 실패 시 reservation cancel 및 presence fail 처리 구현

            - request / txn 분리 구조는 코드 수준에서 반영 완료

        - 현재 수준
            - transfer는 "실제 import/release 로직이 mock인 최소 실행 골격"까지는 올라옴
            - durable transaction 기반으로 단계 추적 가능한 구조가 마련됨

        - 미구현 / 보강 필요
            - 실제 snapshot 내용 구성
            - 실제 target import / spawn 처리
            - 실제 source release / despawn 처리의 강화
            - deadline timeout 처리
            - retry / rollback 고도화
            - allowFallback 사용 및 fallback 정책 연결


    4. Presence / Lifecycle command 분리
    목표
        - presence를 별도 lifecycle 계층으로 분리
        - transfer 과정의 source / target 귀속 상태를 명확히 추적
        - lifecycle command 분리의 기반을 마련

    진행 상황
        - 부분 완료
            - PresenceManager / PresenceRecord 구현 완료
            - AttachToWorld / BeginTransfer / MarkTargetImported /
              CompleteTransfer / FailTransfer / RemovePresence / SetDisconnected
              경로 구현 완료
            - connectionId 기준 presence 관리 및 transfer 연계 완료

        - 현재 수준
            - presence lifecycle은 독립 관리가 가능한 상태까지 분리됨
            - 다만 lifecycle command buffer 체계까지 분리된 것은 아님

        - 미구현 / 보강 필요
            - 일반 command buffer와 lifecycle command buffer의 실질적 분리
            - reentryEligible 활용 정책 보강
            - disconnect 이후 복귀 / 정리 정책 고도화
            - world lifecycle과 presence lifecycle의 프레임 단위 flush 통합


    5. Scheduler 재작성
    목표
        - scheduler를 lifecycle-aware 구조로 전환
        - world stage와 lifecycle flush를 인지하는 실행 모델로 재작성
        - frame end direct commit 구조 제거

    목표
