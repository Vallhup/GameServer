0 Service
 0.1. 개요
  - 서버 프로그램 최상위 관리 Class
  - 서버 실행에 필요한 리소스 초기화 및 수명 주기 제어 역할

  - IGameContext 인터페이스 구현
  - Network Broadcast, 각종 Manager 접근, 시간 정보 제공, ScriptVM 접근과 같은 기능 구현
  
 0.2. 역할
  - Network Core 관리 : Listener, IocpCore, SessionManager 관리
  - GameWorld 관리 : GameWorld 관리하면서 주기적으로 업데이트 (현재 주기는 60Hz)
  - JobQueue 관리 : Tick Thread에서 Enqueue, Logic Thread에서 Dequeue하는 전역 JobQueue 관리
  - (예정) Script VM 제공 : thread-local ScriptVM 관리 / 실제 Script로 돌아가는 객체는 해당 ScriptVM을 참조하고 고유의 Context를 기반으로 동작함

 0.3. 실행 흐름
  - Init() : WinSock, Listener 초기화 / Listener 객체 IocpCore에 Register
  - Start() : Listener, IOCP Worker Thread, Logic Worker Thread, Tick Thread 시작
  - Stop() : Listener 종료, IOCP 해제, WinSock 정리
 
 0.4. 구현 상 중점
  - IocpCore, SessionManager, GameWorld는 명확한 단일 소유권을 보장하기 위해 unique_ptr로 관리
  - Listener는 IocpCore에 등록되는 IocpObject이므로 shared_ptr로 관리

1. Network Core
 1.1. IocpCore
  1.1.1. 개요
   - IOCP객체 관리 Class
   - 내부적으로 IOCP 핸들 생성 및 해제
   - IOCP에 객체 핸들 등록과 Network Event Dispatch 기능 제공

  1.1.2. 역할
   - IOCP Handle 관리 : 생성자, 소멸자에서 IOCP Handle 생성, 해제
   - IocpObject 객체 등록 : IocpObject의 Handle을 IOCP에 등록, 
     IocpObject의 포인터 값을 키 값으로 등록하여 Network Event 발생 시 해당 객체로 연결될 수 있도록 설계
   - IO Event Dispatch : GetQueuedCompletionStatusEx 호출하여 Network Event Get
     가져온 IO Event를 IocpObject의 Dispatch 함수로 전달
   - 이미 정리된 객체(포인터)일 경우 예외 처리 수행

  1.1.3. 실행 흐름
   - Listener, Session과 같이 IOCP에 등록될 객체는 모두 IocpObject Interface 상속
   - 외부에서 Register 함수로 IOCP에 IocpObject를 등록
   - IOCP Worker Thread에서 Dispatch 반복 호출하여 Network Event 수집 
     + IocpObject의 Dispatch함수로 넘겨 세부 처리 진행

  1.1.4. 구현 상 중점
   - IOCP에 IocpObject를 Register할 때 key 값으로 원래 정수형 id를 사용했는데
     Game Framework에서 사용되는 id들과 혼동이 잦아서 포인터 값을 사용하는 방식으로 수정

   - GetQueuedCompletionStatus는 Network 부하가 큰 상황에서 IO Event 수집하는 부분이 
     Bottle Neck으로 평가되어서 GetQueuedCompletionStatusEx로 수정하였음

   - GetQueuedCompletionStatusEx는 IO Event 수집에서의 부하가 크게 줄어들지만
     내부적으로 처리하는 로직(IocpObject::Dispatch)이 그 속도를 따라가지 못하면
     결과적으로 처리되지 못한 Network Packet이 쌓여 오히려 더 성능 부하가 심해질 수 있으므로 Game Framework에서      효율적인 로직 처리를 보장하여야 함

   - 굳이 IocpObject를 shared_ptr로 Register해야할 이유가 없을거 같아서 Law Pointer로
     Register하고 다른 Class(Service, SessionManager)들의 단일 소유권을 unique_ptr로 보장하는 방안 고려중

 1.2. Listener
  1.2.1. 개요
   - 서버 프로그램 Accept 요청 처리 전담 Class
   - Listen Socket 관리, AcceptEx 함수를 통한 비동기 방식 Accept 처리, 
     신규 클라이언트(Session) 접속 시 SessionManager에 등록 요청
   - IocpObject 인터페이스 구현, IOCP 객체에 등록되어 동작

  1.2.2. 역할
   - Listen Socket 관리 : WSASocket으로 Overlapped I/O Socket 생성, 해제
   - 비동기 Accept : 정해진 개수의 AcceptOver 동적 생성 및 AcceptEx 함수 통한 병렬 비동기 Accept 처리
   - 클라이언트 연결 처리 : 신규 클라이언트(Session) 접속 시 SessionManager에 Session 객체 생성 및 관리 요청

  1.2.3. 실행 흐름
   - Init() : Listen Socket Binding 및 Listening 상태 진입
   - Start() : 병렬 AcceptEx 요청 등록
   - Dispatch() : IocpCore에서 Network Event를 Dispatch 함수로 넘겨주면 Event Type 확인 후 ProcessAccept함수에서 처리
   - ProcessAccept() : 신규 Client Socket을 SessionManager로 넘겨 Session 객체 생성 및 관리 요청
   - Stop() : 모든 비동기 Accept, Listen Socket 해제

  1.2.4. 구현 상 중점
   - 초기 ProcessAccept 함수에서 Session 객체 생성 및 관리까지 담당
   - 'Accept 요청 처리' 라는 Listener Class의 책임을 오버하는 기능이라고 판단하여 Session 생성 및 관리 책임을       SessionManager로 이관하였음

 1.3. Session
  1.3.1. 개요
   - 클라이언트 연결(세션) 관리 Class
   - Client Socket 관리, Network IO 처리, Session State 관리 책임

  1.3.2. 역할
   - Client Socket 관리
   - Network IO 처리 : 비동기 Recv, Send 처리 
     Recv 데이터는 RecvBuffer(RingBuffer 기반)에 누적되고 패킷 단위로 잘라져서 핸들러로 전달
     Send 데이터는 SendQueue에 쌓은 뒤 비동기 전송 수행 (Scatter-Gather IO)
   - Session State 관리
   - GameObject 연결 : GameObject Pointer를 보관하여 Game Framework와 연결

  1.3.3. 실행 흐름
   - Listener에서 Client Socket을 만들어 SessionManager에 등록 요청
   - SessionManager에서 Client Socket으로 Session 객체 만들어서 초기화 진행
     (패킷 핸들러 Set, IOCP 등록, 비동기 Recv 시작)
   - SessionManager의 Container에서 관리되면서 Network IO 수행
   - 클라이언트 접속 종료 시 연결 해제(소켓 등 리소스 정리 및 객체 제거)

  1.3.4. 구현 상 중점
   - RecvBuffer를 설계하는 과정에서 단순 배열을 재사용하는 방식과 RingBuffer 도입을
     비교하던 중 단순 배열은 복사 및 관리 비용의 측면에서 단점이 있고 링버퍼는 메모리 재활용이
     효율적이고 모듈화에 이점이 있다고 판단하여 RecvBuffer를 RingBuffer 기반으로 설계하였음

   - 성능 분석 과정에서 WSASend함수의 System Call 오버헤드가 병목지점임을 확인하고
     이를 개선하기 위해 Scatter-Gather IO 방법을 도입하여 다수의 패킷을 1번의 
     WSASend 호출로 처리할 수 있도록 개선하였음, 이 과정에서 내부적으로 멀티스레드 안정성과
     성능을 보장하기 위해 Concurrent Queue를 활용하였음
